# Проектирование ИИ-агента для Ops

[![CI](https://github.com/uMax-Cyber/AgentBlueprint/actions/workflows/ci.yml/badge.svg)](https://github.com/uMax-Cyber/AgentBlueprint/actions/workflows/ci.yml)


![Демонстрация](screenshots/demo.svg)
Паттерны проектирования для запуска слабой LLM (Nemotron-120B) в роли надёжного инфраструктурного агента. Охватывает обучение анти-галлюцинациям, дисциплину использования инструментов, системы памяти и делегирование в команде — всё проверено набором из 36 тестов на боевой инфраструктуре.

## Задача

Слабые модели галлюцинируют параметры, смешивают данные из разных контекстов, не останавливаются, когда данных уже достаточно, и не отличают ошибки инструментов от данных. Этот проект описывает, как обучить и структурировать агента, чтобы он был надёжным несмотря на эти ограничения.

## Основные компоненты

### 1. Дисциплина мышления (SOUL.md)
```
1. Перечитай вопрос — назови точную цель
2. Проверяй, а не выдумывай — каждый факт из результатов инструментов
3. Получи недостающие данные — не отвечай с дырами
4. Сверь черновик с вопросом перед отправкой
5. Доведи дело до конца — проверь, затем отчитайся
6. СТОП, когда данных достаточно — не исследуй лишнего
7. Используй tool_search для обнаружения — никогда не угадывай имена инструментов
8. Инфраструктурная дисциплина — сначала чтение, подтверждение перед изменением
```

### 2. Правила анти-галлюцинаций (9 правил)
Полный набор с примерами — в [docs/anti-hallucination.md](docs/anti-hallucination.md).

### 3. Двойная резервная память
```
LightRAG (семантический поиск) ← ОСНОВНОЙ
        ↓ при недоступности
Файловое хранилище (markdown + grep) ← РЕЗЕРВ
```
Единый интерфейсный скрипт работает с обоими; всегда пишет в оба хранилища.

### 4. Делегирование в команде (Канбан)
```
Агент-оркестратор → создаёт карточки задач → раздаёт исполнителям
Исполнитель (профиль сисадмина) → берёт карточку → выполняет → отчитывается
```
До 9 параллельных исполнителей. Устойчиво к перезапускам с самовосстанавливающимися заявками.

## Методология обучения

1. **Базовый тест** — 36 тестов в 3 доменах (сисадминство, сети, devops)
2. **Анализ первопричин** — классифицировать каждый провал (пробел в инструкциях vs ограничение модели)
3. **Точечное исправление** — добавить правила в системный промпт или файлы навыков
4. **Повторный тест** — те же 36 тестов, измерить улучшение
5. **Итерации** — до 100% проходных результатов

## Результаты

| Метрика | До обучения | После обучения |
|--------|----------------|----------------|
| Общий процент прохождения | 67% (начальный) | 100% (36/36) |
| Уровень галлюцинаций | ~30% ответов | 0% |
| Попытки деструктивных действий | 2/36 тестов | 0/36 тестов |
| В среднем вызовов инструментов на задачу | 15+ (блуждание) | 3-5 (сфокусированно) |
| Таймауты из-за избыточного исследования | 3/36 | 0/36 |

## Архитектура навыков

Каждый навык — это markdown-файл с:
- YAML-шапкой (имя, версия, описание)
- Когда использовать (триггеры)
- Пошаговой процедурой
- Правилами безопасности
- Реальными примерами из продакшена

Примеры — в каталоге `skills/`:
- `tool-discipline.md` — 9 правил анти-галлюцинаций
- `tool-use-patterns.md` — 11 паттернов вызовов с хорошими/плохими примерами
- `wifi-diagnosis.md` — пошаговый диагностический runbook
